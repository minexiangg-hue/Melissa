🔭 产品愿景与差异化

为什么市面上需要又一个英语学习产品？因为现有的产品内容固定、非个性化，而生成式 AI 从根本上改变了这一局面。

📖 传统产品的核心痛点
  • 内容固定：市面产品以背单词/微课为核心，内容千人一面
  • 缺乏互动：口语练习依赖真人外教，成本高、时间受限
  • 无自适应：无法根据用户当前水平动态调整难度和内容
  • 参与感弱：缺乏人格化的"教师"形象，用户难以建立学习情感连接
✨ 我们要做的差异化
  • 人格化虚拟教师：Iconic 角色设计 + 可切换人格，建立情感纽带
  • AI 原生自适应：基于用户画像+英语水平+学习目标，实时生成定制内容
  • 真实语音对话：语音识别 → Agent 处理 → 自然人声合成，全链路闭环
  • 成本革命：目标成本远低于真人外教，甚至低于市面上多数录播课程
  • 情景化学习：未来实现有故事脉络的沉浸式英语学习世界

❓ 立项说明中的关键问题 & 我的回答

🎙️ Q1: 语音识别与语音合成 — 如何实现"不机械"的人声效果？当前能做到吗？

答：完全可以做到，且已有成熟方案。


语音识别 (STT)：

  • 首选 → OpenAI Whisper (API或开源whisper-large-v3)：多语言、强抗噪，英语识别准确率接近人类水平
  • 备选 → Deepgram / Azure Speech，延迟更低、流式支持更好，适合实时对话

语音合成 (TTS) — 核心体验层：

  • 推荐方案一：OpenAI TTS (tts-1 / tts-1-hd) — 自然度高，支持流式，6种预设音色，可直接使用
  • 推荐方案二：ElevenLabs — 业界最佳自然度，支持声音克隆与情感控制，但成本稍高
  • 方案三 (开源自建)：XTTS-v2 / ChatTTS / Fish-Speech — 质量快速提升中，适合长期降本

底层判断：2024-2026 TTS 质量已跨越"恐怖谷"门槛。ElevenLabs 的对话式语音已几乎无法与真人区分。技术的成熟度不是瓶颈，关键在于选择合适的成本-质量平衡点。

✅ 推荐: OpenAI TTS (初期) + ElevenLabs (精品路线)
📚 Q2: 学习资料生成 — 参考数据库 vs 微调模型？你有成熟的方案吗？

答：不走"存教材原文"的路线。推荐构建一套「教材编写指南」——本质是一套内化了英语教学方法的 Prompt Engineering 产物。


核心理念类比：一个有 20 年经验的英语老师，他读过无数教材但从不照抄——他输出的内容是基于方法论内化后的原创教学。我们要在 Agent 里复制的就是这个能力。


方案对比：

维度 ❌ RAG + 教材原文 ❌ 微调模型 ✅ 教材编写指南
数据库里存什么 教材片段/embedding 训练权重 提炼后的教学法元规则（自然语言）
生成方式 检索 → 改写（衍生作品风险） 模型推理 规则驱动原创生成
版权风险 🔴 高 🟢 无 🟢 极低
教学质量 结构有据可循 需大量高质量数据 方法论内化，结构科学
迭代成本 维护向量库 定期重训，成本高 改 Prompt 即迭代

💡 「教材编写指南」如何构建：

输入：多本权威教材（人工阅读、理解、消化）

⬇ 提炼（不是复制）

输出：一套编码在 System Prompt 中的教学法元规则，包括：

  • 各 CEFR 级别的主题范围与典型对话场景类型
  • 词汇/语法引入顺序规律（如"先教现在时再教过去时"）
  • 口语练习形式设计原则（角色扮演、信息差、任务型对话…）
  • 螺旋复习节奏（什么时候复习旧知识、什么时候引入新知识）
  • 纠错策略（什么时候纠、怎么纠、纠到什么程度）

调用路径：用户画像 + CEFR级别 + 这套编写指南 → Agent 生成完全原创的学习资料

关键法律判断："教过去时之前先教一般现在时"是一个教学逻辑，不是版权表达。方法论不受版权保护。我们存的是规则，不是作品。

唯一注意：提炼过程不要自动化批量扒书（爬虫风险）。人工阅读→总结方法论→写入 Prompt——这条路干干净净。

长期（Phase 3+）：积累 ≥10万条高质量用户对话后，微调教学专用小模型（Llama-8B 级别）用于降低推理成本。微调用的是自有交互数据，不涉及第三方版权。

✅ 推荐: 教材编写指南 (Prompt Engineering元规则) → Agent原创生成 → 长期微调降本
📱 Q3: 初始阶段做网站还是移动端/桌面端 App？

答：Web 优先，但要为移动端做适配设计。


决策逻辑：

  • Web 胜在分发：无需安装、一个链接即可分享、迭代速度快 10 倍。对于"验证产品-市场匹配"的早期阶段，Web 是最佳载体
  • 语音在 Web 上完全可行：Web Speech API + MediaRecorder API 已经足够覆盖 STT 场景，AudioContext 可以播放 TTS 音频流。不需要原生能力
  • 移动端 PWA：用 PWA (Progressive Web App) 可以先做到"添加到主屏幕"、离线缓存、推送通知，体验接近原生 App
  • 桌面端 Electron → 后期考虑：初期无需投入，除非需要离线语音处理等原生能力

路线图：

① MVP → 响应式 Web App (桌面+移动浏览器均可)  →  ② 验证后 → PWA (类原生体验)  →  ③ 规模化后 → React Native / Flutter 原生 App

✅ 推荐: Web-first (Next.js + PWA)
🎭 Q4: 人格切换系统与版权问题 — Trump/Snow White 能用吗？

答：需要分两个层面处理。


版权/人格权风险分层：

  • 🟢 安全区：历史公众人物 (Churchill, Einstein, Plato, Shakespeare) — 已过世且属于公共领域；虚构角色原型但不使用其名称和形象，只借鉴"说话风格"
  • 🟡 谨慎区：现代公众人物 (Trump) — 在美国，"声音模仿"可能涉及 Right of Publicity。可以不指名道姓地提供"自信直率、重复强调"的说话风格选项
  • 🔴 高危区：迪士尼角色 (Snow White) — 严格版权保护，绝对不能直接使用名称或形象

推荐实现方式：

不直接说"用Trump风格教你英语"，而是构建一个人格光谱库——用特质标签描述风格（如"自信果断型"、"温柔鼓励型"、"严谨学者型"、"幽默风趣型"），每个风格有独立的 System Prompt。用户选择的是教学风格，而不是名人模仿。这既规避了法律风险，又更贴合教学场景的实际需求。

✅ 推荐: 人格光谱库 (特质标签系统) + 历史人物作为灵感来源

🗜️ Memory Compressor (工具函数)

由 Orchestrator 触发，不是独立 Agent：


  • 将 K 轮之前的对话压缩为结构化摘要
  • 保留关键信息：知识点覆盖、用户犯错模式、情绪轨迹
  • 丢弃无关闲聊和水词
  • 压缩比目标：~3:1（3 轮原始对话 → 1 行摘要）
  • 压缩结果写回状态池，原始对话从窗口移除

为什么不是独立 Agent？压缩是纯工具操作，不需要额外的调度逻辑。减少 Agent 数量 = 减少延迟和 token 消耗。

🔄 对话循环动力学

每一轮用户语音输入如何流经全链路，以及 Orchestrator 如何在不同轮次触发不同操作。

🔁 单轮循环全链路

用户录音 → 听到回应，完整路径：


  1. STT 语音 → 文本
  2. Rule Engine 过滤攻击模式（非 LLM，~1ms）→ 拦截或放行
  3. Guard Agent 输出：意图标签 + 安全标记
  4. Orchestrator 解读意图 → 更新课程快照 → 决定调度策略
  5. Prompt Builder 组装：人格 Prompt + 状态快照 + K 轮对话 + 安全裁剪
  6. Teaching Agent 生成教学回应文本
  7. TTS 文本 → 语音 → 用户听到

目标：端到端延迟 ≤ 2 秒（从用户说完到开始播放回应）

⏱️ Orchestrator 的调度节奏
轮次 Orchestrator 做什么
每轮 读 Guard 意图标签 → 更新课程快照 → 调度 Teaching Agent
每 3-5 轮 检查学生是否偏离课程目标 → 决定是否注入"锚定提醒"到 Prompt
每 5-8 轮 触发 Memory Compressor → 压缩久远对话 → 写回状态池
每节课初 加载用户画像 + 教材编写指南 → 生成本节课课程快照
每节课末 更新学习进度 → 记录薄弱点 → 为下节课预备推荐内容
💡 "滑动窗口 + 持久压缩" — 防止上下文稀释的关键

不保留完整对话历史。像人类记忆一样——压缩成结构化摘要（长期记忆），仅保留最近几轮原始对话（工作记忆）。Memory Compressor 负责这个转换。

同时解决三个问题：

  • ① 上下文不超限（永远只注入 K 轮原始对话 + 摘要）
  • ② Agent 不被用户带偏（课程快照固定了方向锚）
  • ③ 长期学习可追踪（摘要记录知识覆盖和薄弱点演化）

⚠️ 风险评估与缓解

识别关键风险并提前准备应对方案。

风险等级影响缓解策略
语音延迟过高 导致对话体验不自然 🔴 高 用户流失 流式 TTS + 边缘部署 + WebSocket 全双工；目标端到端延迟 <1.5s
LLM 推理成本 难以控制 🔴 高 单位经济学失效 分层模型策略（简单意图用小模型）、Token 限额、长期微调降本
Agent "被用户带偏" 教学效果差 🟡 中 留存率低 三层 Agent Loop + 学习状态摘要锚定 → 已在架构中设计
版权/法律风险 教材素材或人格模仿 🟡 中 法律纠纷 仅用大纲结构不复制内容、人格光谱标签化、法务早期介入
TTS 音色单一 缺乏亲和力 🟢 低 品牌感弱 ElevenLabs 提供丰富音色库 + 自定义声音克隆
用户英语水平评估不准确 🟡 中 内容难度不匹配 多维评估（自评 + 多轮对话采样 + CEFR 标准测试题）+ 用户手动校准
自然语言数据库泄露 用户档案完整暴露 🔴 高 信任崩塌 + 合规风险 存储加密 + 输入过滤 + Prompt 边界隔离 + 审计日志 → 详见数据安全章节
间接 Prompt Injection 恶意用户输入污染库 🟡 中 Agent 行为异常 输入层过滤 LLM 控制 token + 用户内容标记来源和可信等级

🔒 数据安全与隐私设计

以纯 Prompt Engineering 为引擎的系统，后端存放的基本都是自然语言（用户画像、学习进度、对话摘要、教材编写指南等）。这种架构有其独特的安全优势，也有需要正视的风险。

⚠️ 自然语言存储的固有风险

自然语言一旦泄露，立即可读、可理解、可利用。这与结构化数据不同——结构化数据即使泄露也需要"解析和解读"，而自然语言本身就是解读完的结果。


具体风险面：

  • 数据库泄露 = 用户档案完整暴露：用户的学习水平、薄弱点、对话摘要、甚至部分对话原文都在自然语言中，泄露后可直接用于社会工程攻击或竞品分析
  • Prompt Injection 攻击面增大：库中自然语言会流入 LLM Prompt（作为上下文注入），如果库中数据被恶意用户输入污染且未过滤就写入，可能导致间接 Prompt Injection
  • LLM API 提供商看到数据：每次调用 Claude/GPT 时，用户画像和对话以明文经过 API。虽有大厂数据保护承诺，在合规严格场景下仍是考虑因素
  • 访问控制粒度粗：自然语言文本不像结构化字段容易做列级权限——一段用户摘要里同时包含姓名、水平、薄弱点，无法"只让 Agent 看水平但不看姓名"
🟢 自然语言存储的固有优势

但也正因为是自然语言，它天然具备一些安全优势：


  • 无代码执行风险：自然语言规则被 Agent 读取后只是作为生成指引，不涉及代码注入或命令执行
  • 审计友好：自然语言日志比二进制/结构化数据更容易被人类审计——安全事件发生后，可直接阅读日志理解发生了什么
  • 无需反序列化攻击面：不像序列化对象（如 Python pickle），纯文本不会在解析时触发代码执行
  • 备份和恢复简单：纯文本/JSON 格式，不依赖特定数据库版本
🛡️ 分层防护策略
防护层 措施 保护什么
🔐 传输层 TLS 1.3 全覆盖（用户↔服务、服务↔LLM API） 防中间人窃听
🔐 存储层 数据库全盘加密（PostgreSQL TDE / 云服务商 KMS）+ 用户画像字段级可选 AES-256 加密 防物理泄露 / 云服务商侧泄露
🔐 访问层 最小权限原则：Agent → 数据库走专用 Service Account，只授予其职能必需的读/写权限。人类运维不直接访问生产库自然语言字段 防内部越权
🔐 输入层 用户输入在写入数据库前过滤潜在注入标记（如 "<system>"、"<|im_start|>" 等 LLM 控制 token）；所有用户生成内容标记来源和可信等级 防间接 Prompt Injection 污染库
🔐 Prompt 层 从数据库注入到 LLM Prompt 的内容用分隔符包裹 + 明确来源标注，使 LLM 能区分"指令"和"数据" 防库中数据被 LLM 误认为指令
🔐 审计层 所有自然语言数据的读写操作记录到不可篡改的审计日志（append-only）；定期自动扫描库中是否残留敏感个人信息（如真实姓名、邮箱） 事后溯源 + 合规

底线判断：自然语言存储的"可读性"既是风险也是特性——关键不在于不让它可读（加密可以做到），而在于谁有权读、在哪读、怎么读。分层防护的目标是把泄露概率降到足够低，同时保留自然语言的可审计优势。

✅ 核心原则: 传输全加密 + 存储加密 + 输入过滤 + Prompt 边界隔离 + 操作全审计

📏 成功指标 (KPI)

用数据衡量项目是否走在正确的轨道上。

🎯 MVP 阶段 (Phase 1)
  • DAU ≥ 100 (自然增长 + 邀请)
  • 次日留存 ≥ 40%
  • 平均会话时长 ≥ 8 分钟
  • 端到端语音延迟 ≤ 2s
  • 用户反馈 NPS ≥ 30
📈 增长阶段 (Phase 2+)
  • 免费→付费转化率 ≥ 5%
  • 月留存 ≥ 60%
  • 平均月学习天数 ≥ 12
  • 用户推荐率 (K-factor) ≥ 1.2
  • 单位用户毛利 > 0（扣除 LLM + TTS 成本）

🚀 现在就能做的 — 最小可验证原型

完整的 Agent 架构是目标，但我们需要快速验证核心假设。以下是当前可以立即动手、1-2 周内可跑通的最小闭环。

🎯 要验证的核心假设

如果语音对话体验不自然、延迟过高、听起来像机器人——那后面的架构设计再精妙也没用。


第 0 号假设（最高优先级）："用现有 TTS 技术可以实现端到端 ≤2s 延迟的、听感自然的英语口语对话。"


这个假设如果验证失败 → 需要重新评估整个项目的技术可行性。
如果验证成功 → 可以放心投入架构搭建。

🔧 原型范围（刻意最小化）

只做这些：


  • ✅ Web 录音按钮 — 浏览器 MediaRecorder API，点击录音，再点击停止
  • ✅ STT — Whisper API，接收音频 blob，返回转录文本
  • ✅ 一个硬编码的 Teacher Prompt — "你是英语口语老师，用户是 B1 水平。请用英语和他练习对话。每次回复不超过 3 句。" 不需要 Guard、不需要 Orchestrator、不需要状态池
  • ✅ TTS — OpenAI TTS API，把 Teacher 的文本回复转为语音，浏览器自动播放
  • ✅ 测量延迟 — 记录每一步的耗时（STT → LLM → TTS），显示在界面上

不做的：

  • ❌ 没有 Guard Agent
  • ❌ 没有 Orchestrator
  • ❌ 没有状态池 / 记忆压缩
  • ❌ 没有人格切换
  • ❌ 没有用户画像 / 水平评估
  • ❌ 没有 WebSocket（HTTP 请求即可）
  • ❌ 没有数据库
